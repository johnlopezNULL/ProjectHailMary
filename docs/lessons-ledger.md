# Lessons ledger: carried over from an earlier project

Written November 23, 2026. John built and ran an earlier project, a web shop, with AI agents and the
same working method this repo adopted (WORKFLOW.md §1). Each row below started there as a real stop
or defect. The rows are generalized: the shop's details are gone, and each row says what the lesson
means on this project.

This repo's own mistakes go in the never-again ledger, `docs/engineering-playbook.md` §14
(WORKFLOW.md §7). This file does not replace it. Ids here start with CL, for "carried-over lesson"
(CL-01 to CL-48), so they never collide with that ledger's rows or with the playbook's other row
ids. That ledger's seed rows came from the same web shop; six rows here (CL-32, CL-35, CL-36, CL-38,
CL-39, CL-40) restate them for testing. Most rows share one cause; see "The pattern behind most
rows" at the end.

How to read a row:

- **What went wrong** happened on the web shop.
- **Rule** is what to do instead, in general words.
- **Check that enforces it** is the mechanical test, search or self-test leg that makes the rule hold
  without anyone having to remember it.
- **On this project** says what the rule means here.
- **Industry term** is the name a team at work would use. `docs/testing-handbook.md` §12 defines each.
- **Status** is one of three values. `Enforced: <file §>` means the rule is written in that file
  (checked November 23, 2026). `Rule only` means the rule is written here and nowhere binding yet.
  `Planned: with the test bench` means it needs tools this repo does not have yet (the shared test
  bench, the readout, the recorder, the bench manifest) and lands with them.

## 1. Timing and flaky tests

| id | What went wrong | Rule | Check that enforces it | On this project | Industry term | Status |
|---|---|---|---|---|---|---|
| CL-01 | A test script waited a fixed half second after an action and then judged the result; the real system answered more slowly, so the check read the old state and stopped an expensive run although the product was right. The same kind of mistake had caused at least four earlier stops. | Never put a fixed sleep between an action and the read that judges it; wait, with a time limit, for the system's own "done" signal. | Search every harness for sleeps: each one is the interval of a bounded poll or has its reason beside it. The self-test has a slow leg in which every dependency answers after at least 1.5 s. | Poll until a track is CONFIRMED, a node reports ready or the TensorRT engine has loaded, within a deadline. Today `scripts/play_and_echo.sh` sleeps 4 s after starting the bag. | flaky test; explicit wait | Enforced: WORKFLOW.md §16, REVIEW.md "Test tools and harnesses" |
| CL-03 | A check judged a new browser tab's first response with a listener attached after that response had already happened, so the run stopped on a status it could never see. | Never judge an event with an observer attached after the event may have happened; start observing first, or read the state from the source itself. | A capture from an observer started late is kept as a record, never used as a verdict. The reviewer checks the order of "observe" and "act". | Subscribe (start the readout) before the bag or the pipeline starts, or judge from a node's own counters. Every topic here is Volatile (`docs/ICD.md`), so a late subscriber never gets what was published before it joined. The planned ROS-free runtime needs a tested rule for late joiners. | late-joiner problem | Enforced: WORKFLOW.md §16 |
| CL-06 | Without strict rules, a run could not tell "the test read too early" from "the product is wrong", so a real failure could be explained away as flakiness. | A failed read counts as "too early" only when four conditions all hold; it is retried once; when in doubt it is a finding. | The run applies the four conditions from its own record, with both read lines logged, never by judgment. | A threat level, geofence state, intent label or track id is never retried as "too early". The retry stays off until the harness records an action timeline (Planned). | flaky-test triage | Enforced: WORKFLOW.md §6 |
| CL-22 | A check read a cached-by-design source once, straight after a write, and expected the new value at once; the cache still held the old value, so a correct system failed the check after an irreversible step had already run. | Never expect an instantly fresh read from a source that is cached or latched by design; judge from the authoritative source, or poll within its stated freshness window, with a limit, recording every read. | Each judged source's caching or freshness rule is written beside the check before the procedure is used. | No topic is latched today (`docs/ICD.md`); a transient-local topic would hand a new subscriber its last, possibly old, message. The health monitor's rate is a smoothed average (`docs/architecture_diagram.md`), so judge a rate from the source topic's stamps. | cache staleness | Rule only |

## 2. Fakes, fixtures and test environments

CI already builds from a fresh checkout (`.github/workflows/build.yml`). | clean build | Rule only |

## 3. Test tools and the cost of testing

## 4. Designing tests and checks

| id | What went wrong | Rule | Check that enforces it | On this project | Industry term | Status |
|---|---|---|---|---|---|---|
| CL-07 | Tests repeated the code's own expression back at itself, and a release check found an entry by an offset and "verified" it by reversing the same offset, so a badly spliced file passed every gate. | Every fix's test fails with the fix undone, and a check never reuses the computation it checks: the expected answer comes from somewhere else. | The PR lists its mutations (fix undone, test fails); the reviewer asks where each expected value came from. | Expected values for the tracker, association and geofence math come from hand arithmetic, a reference implementation or a recorded output, as in `RangeIsEuclideanNotForwardCoordinate` (`test/unit/test_fusion_engine.cpp`). | test oracle; fail-without-the-fix check | Enforced: WORKFLOW.md §3b, REVIEW.md "Test tools and harnesses" |
| CL-08 | Expectations said "exactly" without saying what was compared or how, described settings in prose instead of naming keys and values, and treated a reused script's bare pass flag as a pass. | Every expectation names what is compared, which read, which fields, and the allowed failures by exact text. | A reviewer flags any "exactly" or "pass" that does not spell out its comparison. | "Tracks match" becomes "track count, id sequence and positions within a stated tolerance, read from named fields over a named window". `scripts/check_outputs.sh` prints WARNING and still exits 0, so it is a diagnostic, not a check. | test oracle; pass/fail criteria | Enforced: WORKFLOW.md §3c |
| CL-05 | A check expected the number of items on the finished page to equal the number in the raw server output; the page's own code re-slices the list, so the run stopped although the candidate matched the base build exactly. | Judge a candidate against the base build measured the same way (same input, settings and waits), never against raw intermediate output or a fixed number. | Each expectation names its base measurement and how it was made; absolute numbers are recorded beside it, not required. | Run the base commit and the candidate on the same bag, launch and clock and compare the readouts within tolerances. During the ROS-free rewrite, old and new runtimes must agree on the same recordings. | differential testing | Planned: with the test bench |
| CL-13 | A page was widened and checked only on its first section at the old sizes; at the widest size its embedded previews broke and sibling pages kept the old width, and the owner found both. | A change to a size, range or capacity is checked on every consumer at the extreme case, with siblings named; a component with modes gets one proof per mode. | A test case at the extreme with an assertion, and a review item that names every consumer. | A change to `TRACK_MAX_TRACKS` (32) or `RADAR_MAX_POINTS_PER_FRAME` (256) in `constants.hpp`, the max range or the frame rate is tested at 0, 1, max and max+1 on every consumer: the association matrix, the fixed containers, the overlays and the planned desktop app's track table. | boundary value analysis; equivalence partitioning | Rule only |
| CL-17 | A run required exact equality on a list it did not control; an unrelated docs merge added an entry and stopped the run before its first step. The same kind of pin stopped three runs. | Use exact equality only for what the run controls; for everything else judge the property that matters and record the value. | A reviewer flags every exact pin on state the run does not control. | Pin the candidate commit, model hash and calibration checksum exactly; judge `main`, uptime, log size or the parameter dump by the property that matters (a 50 ms frame period; no non-default parameter outside a list); compare outputs with tolerances. | over-specified test | Rule only |
| CL-23 | A check for the absence of a summary row matched text anywhere on the page and hit a policy paragraph with the same words, so a false failure stopped a full run. | Assert on the structured thing the check means (a field, an id, a typed value), or match exactly inside a scoped element. | Each string a check matches is searched against the other text it could also hit; a reviewer flags unscoped text matches. | Assert on the typed `threat_level_id` field of `ThreatReport`, not on a search of log text where the same word appears in banners or parameter names. The planned desktop app's tests find widgets by id. | brittle assertion | Rule only |
| CL-27 | A release script compared timestamps carrying microseconds with a millisecond string, so an event exactly on the boundary was counted on the wrong side. | Carry one time representation end to end; at any comparison, convert or round both sides the same way. | A test with an event exactly on the boundary. | Nanosecond integer stamps, seconds as doubles and milliseconds meet in the tracker, the planned recorder and the planned desktop app; test association windows, cutoffs and time sync at their exact edges. | off-by-one | Rule only |
| CL-28 | A test script ran two flows back to back and let the second act before judging the first one's finished record; it also kept a test customer's identifier on an object its results writer saved. | Judge each scenario's finished record before the next one acts; keep personal data out of everything a results writer saves. | A gate between scenarios that blocks on the earlier one's failures; a results writer that refuses an identifier. | A replay suite resets tracker state and judges scenario N before N+1 starts, so track ids cannot leak across scenarios. Camera frames with people in them are personal data and never go into public receipts or this public repo (WORKFLOW.md §5). | test isolation | Rule only |
| CL-30 | Reviewers argued about what re-running a data migration would do until it was run twice on a throwaway database; that showed a skipped statement and a block that would restore the owner's deleted defaults on every re-run. | Prove a data or format conversion by running the real thing twice on throwaway data, empty and filled, not by argument. | The output of the first run and of the re-run, recorded. | The ROS-free rewrite will convert recordings, parameter files and maybe calibration formats; run each converter twice, on empty input and on real data, and compare; a re-run never restores deleted entries or applies anything twice. | idempotency | Rule only |
| CL-32 | An inline default argument became a new object on every screen update and re-triggered a data fetch about 15 times a second; review, the harness and the whole test suite missed it, because the harness injected a stable value in place of the default. | Run one harness pass with production defaults, nothing injected, counting requests or messages per second. | The production-defaults pass, with a rate per topic. | An injected fake clock, sim source or callback means the default path is untested; one replay pass runs with production defaults and a messages-per-second count per topic. | production parity | Enforced: WORKFLOW.md §4 |
| CL-21 | (A standing design rule rather than one incident.) | CL-42 | A list of known harmless console messages named one platform message but not its sibling, so a message present on both builds stopped a run; another list of allowed outside hosts was written from memory and missed hosts the page really loads. | Build an allow-list of harmless noise from a recorded run of the base build on the same machine, matched by pattern, never from memory. | The allow-list cites the run it was captured from. | The list of harmless startup warnings (ROS, TensorRT, the camera driver) is captured from a base-build run on the same board; the Jetson's warnings differ from a desktop build's. | allow-list; baseline capture | Planned: with the test bench |
| CL-43 | A check required something of "every card" in a section, but the page hides some cards on purpose at that screen size, so a hidden card failed the check. | A "for every X" check covers only the X the system means to show; the others are recorded, not judged, and the counts are compared with the base build. | The check states the set it covers; a reviewer asks what the system hides on purpose. | "Every track" checks cover the tracks in the state the check means (for example CONFIRMED); tentative, coasted and deleted tracks (`track_state_ids.hpp`) are recorded, not judged. | equivalence partitioning; differential testing | Rule only |
| CL-44 | A run reached a page no earlier run had reached, and its very first check used text the page does not show exactly; another expected a status the server never returns. | Before a run reaches a state no earlier run has reached, check each expected text, field and value for that state against the source, cited by line. | A static check of every expectation for never-reached states, done before the run. | The first harness run of sensor loss, a geofence breach or a full track table checks its expected field names and enum values against the code and `docs/ICD.md` first. | testing the test code | Rule only |

## The pattern behind most rows

Read the "What went wrong" column again: most rows are not product bugs. They are stops caused by
the test machinery itself: a script that waited a fixed time, a fake that was faster or cleaner than
the real thing, a pin on something the run did not control, a new tool written from scratch.

The web shop measured this. In one audit of 20 stops of its real-environment runs, 14 came from a
test driver or its wrapper, 6 from the written run procedure or its pins, and none from the product.
Over about a month, roughly five of every six ledger rows were stops caused by test tools, and about
66 attempts were needed for 12 passes. On one feature the product code took about 3 hours; the
driver and procedure written for that one feature took about 13 more. Five review rounds on that
driver found real defects but neither of its two timing bugs; a slow test leg and a fake-versus-real
table found both.

What this means here:

- **One shared test bench, extended, never a new rig per feature.** One sim source, one replay
  harness, one readout and one bench procedure, each with a self-test; a feature adds a mode or a
  scene to them (WORKFLOW.md §16). The bench is Planned and not built yet (WORKFLOW.md §15).
- **Features are proved offline.** Unit tests and sim or replay runs carry the proof; the bench runs
  the same standing test every time, plus John's short look (WORKFLOW.md §11).
- **Test-tool time is budgeted and measured** (WORKFLOW.md §9, §11, §17).
- **A test tool's own bugs are caught by its self-test, not by more review rounds** (WORKFLOW.md §3d).

- **This project's own events** (a defect, a hardware miss, a process slip) go into the never-again
  ledger, `docs/engineering-playbook.md` §14, the day they happen, plus a line in REVIEW.md "Repeated
  past findings" (WORKFLOW.md §7). A stop caused by our own harness gets no row anywhere: it becomes
  an assertion in the script or a case in its self-test, so it fails before the next run starts.
